# Upstream Strategy

How Veil relates to Chromium and Brave, which repositories are authoritative,
how Veil's own changes stay separable, and how we will absorb upstream updates
without drowning in merge pain.

---

## 1. Dependency chain

```
Chromium                    the browser engine and platform
   │                        (BSD-3-Clause + component licenses)
   ▼
brave-core                  Brave's layer: patches over Chromium, Brave's
   │                        C++/TS/WebUI features, GN build integration,
   │                        patch tooling ("plaster")
   ▼
Veil                        this repository: our own layer
```

Veil does **not** fork Chromium directly. We sit above brave-core, exactly as
brave-core sits above Chromium.

**Why not fork Chromium directly?** Brave's layer already solves the hard
problems we would otherwise have to solve ourselves: a patch system that
survives Chromium rebases, a GN build that produces a real browser, a supported
`sync`/`build`/`start` command surface, and a release cadence that tracks
Chromium's. Re-implementing that is not our value proposition.

**Why not Electron/Tauri/Qt WebEngine?** They are not browsers. They cannot
provide the process model, sandboxing, site isolation, extension surface,
DevTools protocol surface or permission architecture that an agent-operable
browser requires. This is a hard architectural constraint, not a preference.

## 2. Authoritative repositories

| Repository | Authority over | Role in a Veil build |
| --- | --- | --- |
| `https://chromium.googlesource.com/chromium/src.git` | Chromium source | Declared upstream for `src` by brave-core's `package.json` |
| `https://github.com/brave/chromium` | Chromium mirror | The mirror brave-core's generated `.gclient` actually points `src` at |
| `https://github.com/brave/brave-core` | Brave's layer + build tooling | Cloned to `<workspace>/src/brave`; the thing we layer on |
| `https://github.com/brave/brave-browser` | **Nothing buildable** | Issues, releases, wiki only |
| `https://chromium.googlesource.com/chromium/tools/depot_tools.git` | `gclient`, gn, ninja bootstrap | Fetched to `<workspace>/vendor/depot_tools` |

### The `brave-browser` misconception — resolved

`brave/brave-browser` is a **thin repository**. Its README states plainly:

> "This repository is not needed for building the browser and only holds issues,
> releases and the wiki. The source code and contributions are at
> https://github.com/brave/brave-core."

Its entire contents are `.github`, `.gitignore`, changelogs, `LICENSE`,
`README.md` and a minimal `package.json`. It contains no `config.projects`, no
scripts and no source. It is useful to us only as a release/version signal and a
documentation source.

**Therefore: `brave/brave-core` is the authoritative upstream for everything we
build on.**

## 3. Version pinning

Everything about a Veil build is determined by the pins recorded in
[`../upstream/versions.json`](../upstream/versions.json).

| Pin | Value | Where it comes from |
| --- | --- | --- |
| brave-core version | `1.98.7` | `version` field in brave-core `package.json` |
| Chromium tag | `154.0.8037.49` | `config.projects.chrome.tag` in brave-core `package.json` |
| Chromium repo | `https://chromium.googlesource.com/chromium/src.git` | `config.projects.chrome.repository` |
| depot_tools repo | `https://chromium.googlesource.com/chromium/tools/depot_tools.git` | `config.projects.depot_tools.repository` |

brave-core also declares two `custom_deps` entries as `None` (excluded from
checkout) and two `custom_vars`:

- excluded: `src/testing/libfuzzer/fuzzers/wasm_corpus`,
  `src/third_party/chromium-variations`
- `checkout_clang_coverage_tools: true`, `checkout_clangd: true`

### The real lock file

Pins in `versions.json` are what we *intend* to check out. The build's actual
revision lock is `<workspace>/.gclient_entries`, generated by `gclient sync`,
which "lists out the exact versions that have been checked out".

**Rule: when we publish a build, `.gclient_entries` is the record of truth, and
its contents get copied into `upstream/lock/` for that release.** Do not treat
`versions.json` alone as reproducible.

### Moving a pin

1. Read the new `package.json` from brave-core at the target ref.
2. Update `upstream/versions.json`.
3. Run `scripts/verify-pins.ps1` to confirm the new refs resolve upstream.
4. Re-sync the workspace (`pnpm run sync --init` in `src/brave`).
5. Snapshot `.gclient_entries` into `upstream/lock/`.
6. Re-apply and re-validate Veil's changes; rebuild.

## 4. How Veil's changes stay separable from upstream

This is the single most important maintainability decision in the project.

### The layering rules

1. **Upstream source is never vendored into this repository.** No copy of
   Chromium, no copy of brave-core, no copy of their git history. The workspace
   is fetched, not committed.
2. **Veil's changes live in this repository and are applied to the workspace,
   never edited in place and forgotten.** An edit made directly inside
   `<workspace>/src/...` is invisible to Veil and will be destroyed on the next
   upstream sync.
3. **Prefer the smallest possible change surface.** Before patching
   Chromium/brave-core, check whether the change can be expressed as:
   - a GN arg / build flag,
   - a `.env` value,
   - a Brave feature flag or preference default,
   - a Veil-owned file added via GN,
   - a WebUI override (brave-core has a documented `webui_overriding.md`),
   - a `gni_sources` addition (brave-core has `gni_sources.md`),
   - **only then** a patch against upstream source.

   Every step down that list increases long-term sync cost.
4. **Veil's own code lives in `src/brave/veil/`** (or an equivalent
   clearly-named directory contributed to brave-core's build), not interleaved
   into upstream files. Interleaving is reserved for genuinely unavoidable
   integration points.
5. **Unavoidable upstream edits are recorded as patches**, in the same style
   Brave already uses, so they can be re-applied mechanically after an upstream
   bump.

### What this buys us

- `git` in the workspace stays clean upstream. `git status` there should show
  only expected patch application state.
- Veil's diff against upstream is always inspectable as a bounded set of
  patches plus a bounded set of new files.
- An upstream sync is a mechanical operation with a known failure surface,
  rather than an archaeology project.

## 5. Absorbing upstream updates

Brave's patch system (**plaster**) exists specifically so that a downstream
layer survives Chromium rebases. Veil inherits that machinery for free.

### The sync loop

```
upstream moves
     │
     ▼
brave-core updates its Chromium pin + regenerates its patches
     │
     ▼
Veil updates its brave-core / Chromium pin in upstream/versions.json
     │
     ▼
pnpm run sync  (workspace)   ← re-applies brave-core patches, then Veil patches
     │
     ▼
Veil patches that no longer apply are surfaced and fixed
     │
     ▼
build + test
```

### Rules that keep the loop cheap

- **Never modify upstream files in a way that cannot be expressed as a patch.**
- **Keep Veil's patch count low.** Every patch is a permanent rebase tax.
- **Delete Veil patches when upstream absorbs the equivalent change.** A
  shrinking patch set is a health signal.
- **Track the patch set in the repository**, so `git log` on that directory is a
  readable history of Veil's divergence.
- **Do not chase upstream continuously.** Pin deliberately, move in scheduled
  steps, and validate.

### Anti-patterns we will not adopt

- Editing Chromium directly and losing track of the edits.
- Maintaining a permanent long-lived branch of brave-core that diverges
  structurally.
- Re-implementing Brave build tooling because wiring into it is inconvenient.
- Vendoring a Chrome extension to work around a browser-layer change.

## 6. Keeping removal work cheap

Phase 0 does not remove Brave features yet (see
[brave-customization-plan.md](brave-customization-plan.md)). When we do, the
same layering discipline applies:

- Prefer **build-flag and feature-flag exclusion** over code deletion. A feature
  compiled out by a GN arg does not create a patch that has to be rebased.
- Where deletion is necessary, delete in **whole-file units** where possible,
  and patch only the minimal GN/manifest edges that referenced them.
- Never delete a component until its dependency graph has been traced (see
  Rule 8 of the project rules: do not remove Chromium/Brave components blindly).

## 7. Resolved and open questions

### 7.1 RESOLVED — the hermetic toolchain does not remove the Visual Studio requirement

Phase 0 recorded this as open. It is now **verified from brave-core source**
(`build/commands/lib/config.ts` on `master`):

```
this.useBraveHermeticToolchain = envConfig.getBoolean(
  ['use_brave_hermetic_toolchain'],
  this.rbeService.includes('.brave.com:'),
)
...
if (!this.useBraveHermeticToolchain) {
  env.DEPOT_TOOLS_WIN_TOOLCHAIN = '0'
} else {
  // Use hermetic toolchain only internally.
  env.USE_BRAVE_HERMETIC_TOOLCHAIN = '1'
  env.DEPOT_TOOLS_WIN_TOOLCHAIN = '1'
  env.GYP_MSVS_HASH_3bfcb536c8 = '3dce9a2ec1'
  env.DEPOT_TOOLS_WIN_TOOLCHAIN_BASE_URL = `${this.internalDepsUrl}/windows-hermetic-toolchain/`
}
```

Conclusions:

1. `useBraveHermeticToolchain` **defaults to true only when a Brave-internal
   remote-execution service is configured** (`rbeService` containing
   `.brave.com:`). An external developer has no such service, so the default is
   **false**.
2. When false, Brave sets **`DEPOT_TOOLS_WIN_TOOLCHAIN = '0'`**, which means
   depot_tools uses the **locally installed Visual Studio** toolchain.
3. The hermetic path is commented in-source as **"Use hermetic toolchain only
   internally"** and points at Brave's internal dependencies URL.

**Therefore: a local Visual Studio install with the C++ workload is mandatory
for a Windows Veil build. Brave's hermetic Windows toolchain is not available to
external developers.**

Also verified: the `GYP_MSVS_HASH` variable name in current source is
`GYP_MSVS_HASH_3bfcb536c8` (value `3dce9a2ec1`), not the `GYP_MSVS_HASH_68a20d6dee`
name that appears on the upstream wiki. Trust the source over the wiki.
