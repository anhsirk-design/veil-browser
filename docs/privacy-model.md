# Privacy Model

Veil's privacy commitment — stated precisely, including what is **not** yet
guaranteed.

> **The one-line promise, scoped honestly:**
> Veil sends nothing to Veil-operated infrastructure unless the user explicitly
> chooses that behaviour. Veil also does not pretend that a Chromium-based
> browser makes no network requests — it does, some of them by design.

This document exists because the opposite of a privacy claim is not silence — it
is a false claim. A browser that says "no network" and then checks for updates
is worse than one that documents its traffic.

---

## 1. What Veil guarantees by construction (today)

These are properties of the project itself, not of Chromium.

| Guarantee | How it is guaranteed |
| --- | --- |
| **No Veil analytics SDK** | None is added to the build. Veil ships no analytics code. |
| **No Veil telemetry** | No metrics, events, usage counters, or diagnostics are generated by Veil code. |
| **No Veil ads or ad SDKs** | Veil has no advertising system anywhere in its own code. |
| **No Veil cloud backend** | Veil operates no server that the browser talks to. There is no Veil account, no Veil sync, no Veil cloud service. |
| **No Veil AI provider** | No AI provider is wired in, no key is bundled, no page content is prepared for transmission. |
| **No Veil crash upload** | No automatic error or crash upload exists in Veil code. |
| **No Brave production credentials** | Brave's build-time service keys and endpoints are documented and deliberately **not** supplied. See §3. |
| **No silent opt-in of upstream telemetry** | Upstream telemetry is classified for audit in [brave-customization-plan.md](brave-customization-plan.md) §2.14 and §2.16 — documented, not inherited. |

**What "by construction" means here.** Veil is a thin layer. Absence of code is a
strong guarantee, but it is not the same as verified absence of *behaviour* in a
built binary. Until a Veil binary exists and has been inspected, these are
commitments about the project, not measured results. See §5.

## 2. Known external communication in the foundation

A Chromium-based browser makes network requests. Some are essential; some are
discretionary. Veil inherits Chromium's and Brave's behaviour until it
deliberately changes it.

### 2.1 Required for the web to function

| Class | Why it exists | Controllable? |
| --- | --- | --- |
| **DNS resolution** | Turning a hostname into an address | Yes — DNS-over-HTTPS provider is configurable; secure DNS is the modern default |
| **TLS/OCSP and certificate validation** | Establishing trust for HTTPS | Partially — revocation checking involves third parties |
| **Direct page and subresource requests** | Loading the site the user asked for | It *is* the user's request |
| **WebRTC** | Real-time media | Yes — IP-handling policy is configurable |

These are not "leaks". They are the user's own traffic. Veil's obligation is to
make them understandable and controllable, not to claim they do not happen.

### 2.2 Operational / discretionary, present upstream

These exist in upstream browser software and must be the subject of an explicit
decision, not an assumption.

| Class | What it is | Veil position |
| --- | --- | --- |
| **Component updater** | Chromium fetches updated components (e.g. certificate revocation lists, blocking lists) from Google-operated infrastructure | Audit. Some of this is security-relevant. Veil must state plainly what it fetches and from where. |
| **Field trials / variations** | Chromium's server-driven feature experimentation | Audit. Keep distinct from Brave's own variations system (removed — see plan §2.16). Chromium's is much larger and must be handled deliberately. |
| **Safe Browsing** | Reputation lookups against a service | Upstream notes Safe Browsing requires a Google API key to be **enabled** (`GOOGLE_API_KEY`) **[V]**. Veil treats this as an explicit, documented, user-visible choice — never a silent default. |
| **Search suggestions** | Keystroke-level queries sent to a suggestion provider | Veil position: opt-in, never on by default, and local where possible. |
| **Captive portal detection** | Probe requests to detect a network login page | Audit. |
| **Time synchronisation / network state** | Platform-level connectivity checks | Generally OS-provided; documented rather than controlled. |
| **Extension update checks** | If extensions are installed/updated | Audit, and tied to the extension story. |

### 2.3 Brave-specific communication (upstream, non-Veil)

Brave's layer adds its own endpoints. Each is configured at **build time** via
`.env` flags **[V]**:

- `brave_stats_api_key`, `brave_stats_updater_url` — usage statistics
- `brave_sync_endpoint` — sync service
- `brave_variations_server_url` — Brave's feature rollouts ("Griffin")
- `brave_services_key`, `brave_services_key_id` — Brave service authentication
- `service_key_aichat`, `service_key_stt` — AI chat and speech-to-text services
- `email_aliases_api_key` — email alias service
- `brave_google_api_key`, `brave_google_api_endpoint`, `safebrowsing_api_endpoint`
- `google_default_client_id`, `google_default_client_secret`

## 3. Product-controlled communication

**Today: none.**

Veil operates no endpoint, holds no credential, and ships no code that contacts
Veil-operated infrastructure. There is nothing to disable because nothing
exists. This is the correct starting state and the one we intend to preserve.

The key architectural finding that supports this: **all of Brave's service
credentials are injected at build time from `.env`.** As `../.env.example`
documents, a Veil build supplies **none** of them. A Veil developer build
therefore has no Brave statistics key, no sync endpoint, no variations server and
no AI service key, and consequently no ability to reach those services.

**Important caveat.** Absence of a credential is not proof that a code path is
absent. A build with an empty key may still *attempt* a request that then fails,
may fall back to a different default, or may behave unpredictably. "Inert by
omission" must be upgraded to "removed by design and verified", which is what the
privacy audit in §5 is for.

## 4. What Veil has deliberately not decided yet

Recorded as open, not glossed over:

1. **Safe Browsing.** Keep, replace, or disable? It is a real security benefit
   and a real data-egress channel. It cannot be silently inherited from Brave or
   Google.
2. **DNS and secure DNS provider.** Which resolver, and is it user-configurable
   and documented?
3. **Search and suggestions provider.** No vendor default that cannot be
   explained. Suggestions opt-in.
4. **The component updater.** What is fetched, from whom, how often, and can the
   user see it?
5. **Updates.** Where do Veil updates come from, and what does that channel
   disclose about the user?
6. **Sync.** Whether Veil has one at all, and if so, under whose infrastructure
   and with what key material (self-hostable or not).
7. **Crash handling.** Target state is local-only dumps, never auto-uploaded.
8. **Chromium field trials.** The full disposition of upstream experimentation.
9. **Tor mode.** Whether to keep it, and how to represent it honestly.
10. **Prompt-injection and agent-mediated egress.** Once agents exist, an agent
    is a data-egress path. The permission layer must cover it before agents ship.

## 5. The privacy audit (required before any privacy claim)

No claim in this document should be treated as *verified* until a Veil binary
exists and the following has been done with the network observed:

1. **Baseline capture.** Cold start, idle, no page loaded. Record every outbound
   request: host, path, trigger, and whether it is suppressible.
2. **Navigation capture.** Load representative real sites. Separate first-party
   traffic from third-party telemetry.
3. **Feature-surface sweep.** Visit each settings/preferences surface and each
   browser feature; watch for requests triggered by opening UI rather than by
   user intent.
4. **Binary inspection.** Confirm no Veil-added analytics/telemetry symbol or
   endpoint string is present.
5. **Credential check.** Confirm the built binary carries none of Brave's
   service keys or endpoints.
6. **Update-path check.** Confirm what the update mechanism contacts.
7. **Failure-mode check.** Block the network and confirm the browser degrades
   gracefully — a failed request must not become a fallback request to somewhere
   unexpected.
8. **Document the result** in this file, replacing assumptions with measurements,
   and move verified items from "open" to "resolved".

Upstream Brave already ships a network-audit test suite — brave-core's
`package.json` exposes a `network-audit` script (`brave_network_audit_tests`)
**[V]**. That is the natural starting point for step 1–3 rather than writing
something from scratch, and it should be examined early in the build phase.

## 6. Future privacy architecture (intended, not built)

Design principles for the eventual system. None of this exists yet.

- **Disclosure over default-deny fiction.** The user can see, in one place, what
  the browser can send and is sending.
- **Purpose-bound permissions.** A capability granted for one purpose does not
  silently extend to another.
- **Local-first.** Anything that can happen locally happens locally. No remote
  default for a capability that has a local implementation.
- **Per-capability egress control**, at a granularity a technical user actually
  wants (per-origin, per-service-class, per-agent).
- **Agent parity.** An agent is a principal with no more authority than a
  grant explicitly gives it, and every exercise of that authority is recorded.
- **No silent provider.** Any AI/model provider is user-configured. Local models
  are first-class. There is no Veil-preferred provider.
- **Inspectable by construction.** A user who wants to verify behaviour can,
  without a debugger attached.
- **Recoverable.** Blocking too much must never leave the browser unusable.

---

## 7. Rules this project will not break

1. Do not add an analytics or advertising SDK.
2. Do not add product telemetry.
3. Do not add a Veil cloud service.
4. Do not bundle an AI provider or its key.
5. Do not auto-upload crash or diagnostic data.
6. Do not inherit upstream telemetry endpoints or credentials by default.
7. Do not claim privacy properties that have not been verified against a built
   binary.
8. Do not remove security-critical upstream systems merely because they touch
   the network — document, decide, then act.
